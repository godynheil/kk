KK VCS: Large-File Version Control
Built for Game Developers

KK (KK Version Control System) keeps your source code in Git and your large binary assets - textures, models, audio, video - safely stored, SHA-256 verified, and simple enough for solo developers to run without extra infrastructure.

Simple by Design.

Step 1 - Initialize

Run kk init in your project root. KK creates a local .kk/ directory containing a bare Git repository and an object cache.

Step 2 - Track Assets (Optional)

KK tracks all non-code files automatically by default (e.g. .uasset, .unitypackage, .fbx). You can configure custom patterns if desired: kk track "*.psd" "*.fbx" "*.wav".

Step 3 - Stage and Commit

kk add . stages your changes. kk commit creates a Git commit with pointer files for tracked assets and full file content for everything else.

Step 4 - Connect a Remote

kk setup gdrive walks you through Google Drive authorization in your browser using OAuth 2.0 with PKCE. Or configure a local path or rclone remote manually.

Step 5 - Push and Pull

kk push uploads new objects to your remote(s) and syncs the manifest. kk pull downloads missing objects to your local cache on demand.

Step 6 - Verify Anytime

kk fsck verifies every object referenced by your history is present and intact - locally and on the remote.

Everything Git Handles, Plus Everything It Doesn't.

Git-Native Workflow

KK wraps Git. Your branches, merges, commits, tags, and history stay exactly where they belong - in a standard Git repository. KK adds large-file management on top, not in the way.

SHA-256 Asset Verification

Every large file is stored as a content-addressed object identified by its SHA-256 hash and byte size. Uploads and downloads are verified automatically. Corruption is detected before it silently reaches your team.

Bring Your Own Storage

Push to Google Drive, a NAS, a local folder, MEGA, or any rclone-supported destination. No vendor lock-in. No monthly SaaS fee. No server to maintain. Your assets live where you decide.

Multi-Remote Support

Configure multiple remotes - a fast local NAS for the studio and Google Drive as an offsite backup. KK can push to all of them and pull from the best available source automatically.

Pointer-Based History

Git commits a tiny pointer file for each large asset - not the raw bytes. Your repository stays lean. Large objects are pulled on demand, only when needed.

Deduplication

Objects are stored once per unique SHA-256 hash. The same texture used across ten commits is stored exactly once on your remote. Storage costs stay low.

Integrity Checking

Run kk fsck to verify that every object referenced by your Git history is present and intact - locally and on your remote. Catch missing or corrupted assets before a deadline.

Zero Telemetry

KK never phones home. No analytics, no crash reports, no usage tracking. The Licensor has zero visibility into your projects, your files, or your workflows.

Your Data Is Yours. Always.

KK runs entirely on your machine.

No data is sent to KK servers - because there are no KK servers. Your files, your credentials, your repository history, and your project metadata never leave your local machine or your chosen storage backend.

Google Drive OAuth tokens are stored locally with 0600 file permissions. KK requests only the drive.file scope - it can only see files it creates.

Frequently Asked Questions

Q: Does KK replace Git?
No. KK wraps Git. Your Git history, branches, tags, and commits are all standard Git and can be used with any Git host (GitHub, GitLab, Bitbucket, Gitea, etc.).
Q: Do I need a KK server or account?
No. KK is a local CLI tool. There are no KK servers, no KK accounts, and no subscription required for non-commercial use.
Q: How is KK different from Git LFS?
Git LFS requires a dedicated LFS server (or a SaaS LFS host). KK stores objects in any location you configure - a local folder, Google Drive, NAS, MEGA, or any rclone backend. KK also embeds its own Git repository so it doesn't depend on your host's LFS support.
Q: Is KK open source?
KK is source-available under the Modified GNU General Public License, Version 2.0 (Modified GPL 2.0). Non-production use is free. Each version converts to Apache 2.0 four years after its release. Commercial Production Use requires a separate license.
Q: What data does KK send to the developer?
None. KK has zero telemetry. It collects no analytics, crash reports, usage statistics, or diagnostics of any kind.
Q: What happens to my Google Drive credentials?
OAuth tokens are stored only on your local machine (%APPDATA%\KK\gdrive\ on Windows, ~/.config/KK/gdrive/ on macOS/Linux) with restrictive file permissions. They are never transmitted to the KK developer or any third party.
Q: Can I use my own Google OAuth credentials?
Yes. Set KK_GOOGLE_CLIENT_ID and KK_GOOGLE_CLIENT_SECRET environment variables before running kk setup gdrive.

Git Was Not Built for Large Files.

Textures, 3D models, audio banks, and video files break standard Git repositories by bloating their history and making clones unmanageably large.

Git LFS (Large File Storage) is the industry standard for handling large files in Git. However, it requires Git hosting providers that support LFS (often incurring additional storage fees), relies on servers implementing the specialized Git LFS API, and doesn't natively target standard consumer cloud services or local network storage.

KK is not a full or general-purpose replacement for Git LFS. Instead, it is an alternative designed for a different usecase: it allows solo developers and small teams to store large assets directly on storage they already own (such as Google Drive, a local NAS, or any cloud provider supported by rclone) without hosting separate LFS infrastructure.

Not for Everyone.
Built for Teams with Storage Constraints.

KK is not meant to be useful to everyone. If your project has no large files, no storage constraints, and no reason to separate source history from asset storage, it is probably not for you.

It is built for developers and small indie teams with a lot of storage, limited infrastructure, or a preference to avoid setting up and maintaining SaaS or dedicated file servers. Some teams already have a NAS, Google Drive, MEGA, S3, Backblaze B2, or another storage target available, and only need Git to track the regular files, project history, and small pointer files.

This is useful when a repository contains source code beside heavy assets: game projects, art-heavy prototypes, video/audio work, modding projects, machine-learning datasets, local tools, build artifacts, or any workflow where binary files are too large or too frequently changing to keep directly inside Git history.

It also fits teams that want a simple, inspectable setup: Git for commits and collaboration, ordinary storage for large objects, and no requirement to adopt a specific hosting platform just to move files around. A solo developer might use Google Drive. A small studio might use a NAS. A distributed team might use rclone to push to S3, B2, MEGA, or another backend they already pay for.

KK does not try to turn GitHub or GitLab into asset storage. Those providers are best used for normal source files, reviews, issues, CI, and the pointer files that describe which large objects belong to each commit. The actual large objects stay outside the Git provider, where storage is cheaper, easier to replace, and under your control.

That is the point of KK: Git providers such as GitHub, GitLab, Bitbucket, or Gitea can keep doing what they are good at, while the heavy binary objects live on the storage backend you choose.
